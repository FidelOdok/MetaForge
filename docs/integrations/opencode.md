# Use MetaForge from opencode

[opencode](https://opencode.ai) can drive MetaForge as a remote MCP server.
`integrations/opencode/` is a package for it, generated by
`scripts/build_integrations.py` from the same sources as the Claude Code and
Codex packages and versioned with them through
`integrations/plugin-version.json`. It holds:

| Part | opencode form | From |
|---|---|---|
| The `metaforge` MCP server, at the hosted gateway | `mcp.servers.metaforge` in `opencode.json`, `type: "remote"` | the hosted gateway address the cloud package uses |
| 14 slash commands, `/metaforge/<name>` | `commands/metaforge/<name>.md` | the curated workflows, with Claude Code wording adapted |
| 3 subagents | `agents/metaforge-*.md`, `mode: subagent` | the Claude Code plugin agents |
| The skills | `skills/metaforge/<id>/SKILL.md` | the same skills the Claude Code package ships |
| Working rules | `metaforge-rules.md`, listed in `instructions` | the rules the Claude Code SessionStart hook adds |

## Install

```bash
git clone --depth 1 https://github.com/FidelOdok/MetaForge.git
sh MetaForge/integrations/opencode/install.sh --project /path/to/your/project
# or, for every project:
sh MetaForge/integrations/opencode/install.sh --global
```

`--project` installs into the project's `.opencode/` folder and `--global`
into `~/.config/opencode/` (or `$XDG_CONFIG_HOME/opencode`). The script copies
the commands, agents, skills and rules, then adds the `metaforge` server and
the rules file to the `opencode.json` in that folder:

- other settings are kept, and the previous file is saved as `opencode.json.bak`;
- a `metaforge` server that is already configured is left as it is;
- a config that still uses the V1 shape (servers directly under `mcp`) gets
  its entry in that shape;
- an `opencode.jsonc` with comments is not rewritten: the script prints the
  entries to add and exits non-zero.

Running it again is safe. It needs `python3`.

## Sign in

```bash
opencode mcp auth metaforge
```

Sign in with your MetaForge email and password, the ones you use on the
dashboard. The gateway answers 401 and opencode runs OAuth (the gateway
offers dynamic client registration), then stores the credentials outside
your configuration. You reach only your own account's projects. `/mcps`
inside opencode does the same, and `opencode mcp logout metaforge` signs out.

The package carries no API key and no `Authorization` header, and leaves
OAuth on. An API key bypasses the per-account scope the sign-in gives.

## Writes wait for a human

The hosted gateway sees opencode as a remote caller, so a tool that writes
is held for approval. Held calls appear on the dashboard's Approvals page,
and `/metaforge/approvals` lists them.

## Tool names

opencode names an MCP tool `<server>_<tool>`, replacing anything other than
letters, digits, `_` and `-` with `_`. MetaForge's `flow.propose` is therefore
`metaforge_flow_propose`, and under opencode's default Code Mode it is called
as `tools.metaforge.flow_propose(...)`. The skills and commands name tools by
their MetaForge id; the rules file states the mapping.

The gateway's MCP prompts also appear once you are signed in, as
`/metaforge:<name>`. They are the same workflows in client-neutral wording.

## How the formats were established

From the opencode 2.2.5 binary and the V2 documentation it points at
(`https://opencode.ai/v2/docs/`), not the V1 documentation:

| Part | Format |
|---|---|
| MCP server | `mcp.servers.<name>`; remote servers use OAuth unless `oauth: false` |
| Commands | `command/` or `commands/`, `**/*.md`; the path below that folder is the name; frontmatter `description`, `agent`, `model`, `subagent` |
| Agents | `agent/` or `agents/`, `**/*.md`; frontmatter `description`, `mode` (`primary`, `subagent`, `all`), `model`, `permissions`; `name` and `tools` are V1 fields |
| Skills | `skills/**/SKILL.md`, read natively; the id is the folder name |
| Rules | `AGENTS.md`, or files listed in `instructions` |

The package was then loaded by opencode 2.2.5 with a scratch home directory,
installed both per project and globally. `opencode mcp list` reports
`metaforge  needs authentication`, `opencode debug agents` lists the three
agents as subagents, the server's command and skill lists include every
MetaForge command and skill, and the log shows the rules file loaded from
`instructions` with no warning about any packaged file. Signing in and
calling a tool were not exercised, since they need an account.

## What does not carry over

- **The reminder after a held proposal.** Claude Code's PostToolUse hook
  restates that a held `flow.propose` or `flow.patch` waits for a person.
  In opencode that is a line in the rules. A plugin could add it from a
  tool `execute.after` hook, but MCP tools run inside Code Mode by default
  and that path could not be checked without signing in.
- **Agent model choice.** The Claude Code gate reviewer asks for `opus`;
  opencode wants a `provider/model` id, so the agents use the session's model.
- **Reasoning capture.** Tool calls are recorded server-side once connected;
  a client plugin that sends reasoning to `/sessions` is not written yet. See
  [Agent session capture](../session-capture.md).
