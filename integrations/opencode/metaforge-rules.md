# MetaForge working rules

From the MetaForge package for opencode: the plugin attaches it to each new session, and an install.sh install lists it under `instructions` in opencode.json. Generated by `scripts/build_integrations.py`; do not edit by hand.

MetaForge plugin rules for this session:
- Never use an engineering value without a source. Find it (user, project documents, standards, past work, components and stock, analysis, measurement) and record it as a design_value with its source; a default only as a stated assumption for the person to review. Budget, quantity, machines and look come only from the user; 'unknown' is a valid answer.
- Before proposing a design flow: flow.compile_intent, then flow.capabilities. Propose with template AND operations together (never template alone).
- Proposals, patches, gates and waivers are approved by a person. No tool approves; report the approval id and stop.
- When a MetaForge result says approvals are waiting for a person, tell the person right away and offer /metaforge/approvals; approvals.decide puts one to them in a prompt. Never answer one or report it as decided.
- When review.list_tasks shows open gate reviews, hand them to the metaforge-gate-reviewer subagent; never review a phase you worked on.
- A design is done only when flow.lifecycle / flow.verify_completion says COMPLETED_VERIFIED. PARTIALLY_COMPLETED is not done.
- 'unknown' phase state is not 'pending'; no_data is a gap, not a pass.
- Before custom hardware design, check the project/library and complete commercial or open hardware modules first. Compare hard requirements and interfaces; record why unsuitable modules were rejected before building from individual parts. Unknown specifications and missing executable models are gaps, never passes.
- When a selected library component has models, read its pinned usage and limitations with library.resolve_component_model before loading it into an engineering tool. Fetch binaries only for the operation that needs them; record the lock hash with the resulting evidence.
- When `flow.propose` or `flow.patch` comes back with status `proposed`, the approval it names is held for a person. Nothing runs or changes until they answer it. Report the approval id and stop; do not poll, and do not look for a way to approve it.
Skills: intent-to-verified-design (procedure), workflow-lifecycle (reasoning).

## Tool names in opencode

Skills, commands and agents name MetaForge tools by their id, such as `flow.propose` or `twin.get_node`. opencode names the `metaforge` server's tools `metaforge_<id>` with the dot turned into an underscore: `metaforge_flow_propose`, `metaforge_twin_get_node`. Under Code Mode they are `tools.metaforge.flow_propose(...)`. Read a resource such as `metaforge://twin/brief/<project_id>` with `read_mcp_resource` on the `metaforge` server.

## Writes wait for a human

The gateway sees opencode as a remote caller, so a tool that writes is held for approval and appears on the dashboard's Approvals page. opencode does not show MetaForge's approval prompt (it files the form outside the session), so when a call comes back held, tell the person they can type `/metaforge/approve` or `/metaforge/decline` (optionally followed by the approval id), or decide it on the Approvals page. Never type those commands or answer a prompt yourself, and do not retry until they have answered. When a message says the person approved it, make the identical call again once. A refusal names what happened (`rejected`, `timed_out` or `not_configured`); none is worth retrying until a person has done something.
